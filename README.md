| Streamlit | 部署后为 `https://<app-name>.streamlit.app` | 不能，同上 |

**为什么只有共享版能同步**：云端服务做「精确来源匹配」（exact Origin match）。来自未登记域名的请求会被直接返回 `403 access_denied: the request origin is not allowed for this client`，而且浏览器读不到这个响应体，只会表现为「连不上」。所以看板在打开时会先本地比对当前域名，域名不对就直接降级为本机模式并给出跳转链接，不让人对着一个永远连不上的地址排查。

⚠️ 如果以后重新创建云服务应用，`applicationId` 会变，endpoint 与白名单域名也会跟着变，此时必须同步更新 `build_v5.py` 里的 `CLOUD` 配置并重新发布，否则同步会失效。

### 总部地图的口径（2026-11 修订）

地图上的点有三种来源，**视觉上必须能区分**，否则会把「州中心」误读成「总部位置」：

| 精度 | 什么样的客户 | 画法 | 位置含义 |
|---|---|---|---|
| `city` | 简介里能解析到具体城市 | 实心圆 + 城市名 | 真实总部城市坐标 |
| `state` | 只解析到州 | 空心虚线圆 + 「加利福尼亚（州）」 | **该州几何中心，不是总部** |
| `province` | 只解析到加拿大省份 | 空心虚线圆 + 「不列颠哥伦比亚（省）」 | **该省几何中心，不是总部** |

配套规则：

- **不拿简介短语当城市名**：`parseHQ()` 查不到城市时，`city` 置空，原文片段只留在 `rawCity` 里供悬停追溯。之前「主营面向全美」「采用全远程模式」「主枢纽位于西海岸」「覆盖纽约-宾州」这些描述被当成城市印在地图上，位置还落在州中心。
- **同城不会被拆成两个标签**：多伦多曾有 7 家精确城市点 + 8 家省级兜底点（省份中心恰好也是多伦多），合并后是一个簇。
- **大簇不冒用单城市名**：合并了多个城市的簇（90km 内）标成「纽约一带」，悬停里列明含哪几处，不再出现整个纽约都市圈被叫成「法明代尔」。
- **标签避让按真实宽度算**：中文 9.2px/字、英文 5.4px/字（原来一律 6.6px，中文被低估 24%，避让形同虚设）；12 个候选方位都放不下就不标，悬停仍可看，完整清单在右侧「都市圈 Top」。宁可少标，不叠字。
- **州名一律中文**：`STATE_CN / PROV_CN` 反查，同一英文名取最长的中文写法（避免「加州」把「加利福尼亚州」覆盖成单字「加」）。
- 右侧「定位覆盖」拆成 `精确到城市 / 仅到州 / 仅到省 / 未定位` 四档，未定位的客户名可展开查看；简介里没写总部的一律不猜。
- 画布上限为北纬 52.6°，加拿大北部超出视野，顶部用渐隐过渡而不是硬切。

代码位置：`src/geodata.js`（`parseHQ` / `attachHQ`）、`src/views_map.js`（`cluster` / `placeLabels` / `view`）。

### 目标行业维度（2026-11 新增）

在「零售商 / 代理集成商」之上再加一层：按「一句话简介」判**客户主要服务的行业**。核心口径是**看它卖给谁，不看它怎么卖**——
摄影器材店写「面向专业摄影师与影视剧组的摄影器材零售商」，判「摄影·影像」而不是「零售·电商」；只有大型综合零售 / 电商才归「零售·电商」。

14 个档位：教育 · 摄影·影像 · 影视·广电 · 政府·公共 · 医疗·健康 · 会议·协作 · 现场活动·租赁 · 体育·电竞 · 宗教场所 · 住宅·智能家居 · 安防·监控 · 企业·办公 · 零售·电商 · 综合·多行业（另加「未标注」）。

判定规则（`src/classify_industry.py`）：

1. 场景词按权重累加（专有场景词 3 分，泛词 1 分），同一词最多计 2 次；
2. 「服务 / 面向 / 专注 / 为 ……」后 16 字内命中的行业再 +3 分（明写服务对象的优先）；
3. 首次出现位置在前 40 字内 +1 分；
4. 得分 ≥4 的类别 ≥3 个 → 「综合·多行业」（简介写「服务政府、教育与医疗」这类就落这里）；
5. 只有「零售 / 电商 / 企业 / 租赁」这种泛线索时，按证据最强者归类并在依据里注明「证据偏弱」；
6. 只写 IT / AV 集成与分销、没提行业 → 「综合·多行业」；简介里什么线索都没有 → 「未标注」，**不硬猜**；
7. 判错的写进 `data/industry_override.json`（客户名 → 结论 + 理由），优先级最高。

当前分布（823 家）：综合·多行业 108、影视·广电 137、现场活动·租赁 75、零售·电商 70、摄影·影像 63、住宅·智能家居 62、宗教 43、安防 42、企业办公 40、教育 32、政府 31、会议协作 29、体育电竞 18、医疗 13、未标注 42（5%）。

界面上：顶部筛选栏「行业」下拉、总览「目标行业分布」环形图、P 码总表与跟进表客户名旁的行业标签、客户主表独立列、客户详情里的「目标行业」区块（含判定依据与关键词）。

## 搜索框是全库搜索（2026-11-20）

顶部搜索框一个输入框干两件事：

1. **仍按原样筛选当前这张表**（`state.filters.q`，160ms 防抖，搜名字 / 简介 / 覆盖范围 / 竞品）；
2. **额外弹出「全库结果」面板，同时查零售商 + 代理集成商**——以前在零售商页搜代理商名字是「什么都没搜到」，
   而两侧本来就是同一份 `APP.customers`，只是分页展示。

面板细节：

- 每行给：客户名 + 类型标签（零售 / 代理）+ P 码 + 国家；
- 排序：名称完全相等 > 名称开头 > 名称包含 > 只在简介/国家/竞品里命中；同分时当前侧优先；
- 点**本侧**结果 → 直接开客户详情；
- 点**另一侧**结果 → 写 `#t=<类型>&v=<当前视图>&open=<客户id>` 后刷新，落地页渲染完自动打开该客户详情
  （两侧口径不同、抽屉内容按类型渲染，混在一个页面里开抽屉会串味，所以用刷新切换而非就地渲染）；
- 多关键词空格分隔，**每个词都要命中**（`Staples 加拿大`）；
- 一处都没有时明确写「两侧都没有匹配」，不留空白；`Esc` 或点空白处收起，`Enter` 开第一条。

## 跟进历史（每次修改自动留痕）

点击客户弹出的抽屉里，跟进记录下方有「跟进历史」时间线：**每次跟进字段落库都自动追加一行**

- 写入点在 `src/sync.js`：`push()` / `flush()`（手动改）与 `savePipe()`（批量导入）都会调 `logHist()`。
- 读取：抽屉打开时 `hist(id)` 按 record_id 查最近 60 条；编辑保存后 600ms 自动补一条。

## 备注里写「某某 代理」→ 自动挂代理商标（2026-11 新增）

在**跟进备注**（抽屉里那个可换行的备注）、或**原表 / 录入备注**里写一句
「PK Distrubution 代理」，看板就会在行业标签后面自动加一枚 **`PK Distrubution 代理`** 标签，
出现在：P 码总表（客户名后）、开发跟进表（第二行行业后）、客户主表（目标行业列）、抽屉头部。
鼠标悬停显示命中的备注原句与来源，方便核对识别得对不对。

**固定写法：`某某 代理`（品牌与「代理」之间一个空格）。** 两字品牌（PK / LG / 3M）照样认，
中文两字品牌请留空格（`影石 代理` 认，`影石代理` 不认——避免「本地代理」这类泛词被当成公司名）。

识别规则（`core.js: agentMention()`，宁可少识别也不误判）：

| 备注写法 | 结果 |
|---|---|
| `PK Distrubution代理` / `联系人 Mike，PK Distrubution 代理，下周约会议` | ✅ PK Distrubution 代理 |
| `Staples 由 PK 代理`、`Staples 由PK代理`、`由 LG 代理`、`3M 代理` | ✅ 两字品牌连写也认（ASCII 品牌） |
| `联想 代理`、`渠道由 影石 代理` | ✅ 中文两字品牌，带空格 |
| `Staples 由 PK Distrubution 代理`、`改由 Ingram Micro 区域代理，原 PK 已终止` | ✅ 按「由 / 改由 / 交给 / 换成」截断，只取最后一段 |
| `由 PK Distribution 总代理`、`Exertis 独家代理`、`联系人 Mike（Exertis 代理）` | ✅ 总代理 / 独家代理 / 区域代理 / 一级代理等后缀都认 |
| `代理商是 TechData，报价走他们`、`代理方：TechData` | ✅ 倒装写法也认（必须有 是 / 为 / ：连接） |
| `这家是代理`、`我们是代理商`、`他们做代理和零售` | ❌ 不显示（指代词） |
| `增值分销代理商`、`区域代理模式为主` | ❌ 不显示（只是身份描述，不是公司名） |
| `2B 代理`、`B2B 代理`、`2C 代理`、`按主要 2B 口径归代理侧` | ❌ 不显示（**业务口径词**，2026-11-19 新增） |

| `代理业务占比 60%` | ❌ 不显示（倒装式要求有 是/为/：） |

- 名字长度限 **2–44** 字符，遇标点 / 换行 / 括号断开；识别不到就**不出标签**，绝不替用户猜一个代理方。
- 2026-11-19 修改原因：旧规则下限是 3 字符，把 `PK 代理` 这类两字品牌挡掉了；
  同时真实数据里 4 条重分类留痕（`按主要 2B 口径归代理侧`）被误挂成代理方标签。现在两字品牌放行、口径词与行业缩写挡掉。
- 标签是**实时从备注算出来的**，不是单独存的字段：改备注或清空备注，标签跟着变（回归里有断言）。
- 数据口径：备注本身存在 `pipe_records.note`（跟进备注）或源表 / `customers_extra` 的备注字段，
  没有新增任何云端列，所以同事不用重跑建表 SQL。

## 客户竞品信息 ⇄ 竞品面板 打通（2026-11-19 新增）
客户侧填的竞品信息，现在会汇总进竞品页，两边都能点着走。涉及三处数据源：

| 来源 | 字段 | 解析方式 |
|---|---|---|
| 结构化（零售） | `头部竞品品牌体量` | 按 `、，/\n` 切词；体量列已有 SKU 与价格带，直接采用 |
| 结构化（代理） | `合作竞品` | 按换行切词，跳过「官网未揭露」「/」等噪声 |
| 自由文本 | `一句话简介`、原表 `备注`、跟进备注、开发难点 | 品牌词表匹配，带原句 |

### 「头部竞品品牌」列已删除（2026-11-19）

源表第 J 列「头部竞品品牌」不再作为看板字段出现：原表只有 6 行有值，且内容与 K 列「头部竞品品牌体量」重复。

- **数据没动**：源表仍按原样读入（`source_latest.json` 里那 6 行原文还在），只是客户详情的「原表字段」区不再渲染这一格，
  批量导入时也直接忽略这一列。
- **解析改以体量列为准**：竞品关联只从 K 列 + 简介 + 备注出。代价是 Adorama 少了 4 个只有 J 列才写到的品牌
  （Yealink / BZB GEAR / Lumens / AIDA），把它那句补进「头部竞品品牌体量」即可原样回来。
- 连带影响：竞品页「来源」不再出现「品牌列」，只剩「体量列 / 合作竞品 / 简介 / 备注 / 跟进备注」。

### 体量列的三种写法（2026-11-19 补）

有的客户不是按「品牌: N SKU」记的，这两种也算数：

| 写法 | 例子 | 结果 |
|---|---|---|
| 标准 | `Logitech: 31 SKU` | 品牌 31 个 SKU（原逻辑，未动） |
| **叙述式** | `Logitech 8 款、Rapoo 5 款、ISY 4 款（MediaMarkt 自有品牌）、HP 2 款…榜单前 10 名中有 7 个自营：Logitech 3 款` | 拆出 7 个品牌；括号里的「自有品牌 / 型号举例」不算品牌名；同品牌取**最大值**（8 款，不是 8+3） |
| **只有品牌名** | `Logitech、Insta360、Razer`，或一行一个品牌（GoElectronic 9 个） | 照样关联，SKU 记「—」，**不填 0** |

- **品牌名自带数字不影响识别**：`Insta360` 里的 360 不是款数。2026-11-19 之前这里用「文本里一个数字都没有」来判断
  要不要走「纯品牌名」兜底，导致体量列写 `Logitech、Insta360` 的客户（如 BCC）一个竞品都没关联上 —— 现在无条件走兜底，
  同一品牌靠 key 合并、SKU 只取更大的值，不会重复计数。
- **中文词只认底表登记过的别名**（罗技 / 影石 / 圆展…），底表里没有的中文串一律不当品牌 ——
  `1000DKK以上价格带`、`门店不售`、`榜单前 10 名中有 7 个自营` 这类句子碎片不会污染竞品页；拉丁写法照旧收
  （4XEM / Blackmagic Design / Inland 这些原表里真实出现、底表还没登记的品牌仍然有效）。
- 切词是**括号感知**的：`OBSBOT（Tiny 2 Lite、Tiny 3 Lite）2 款` 里的「、」属于括号举例，不会把括号劈开导致
  `Tiny 3 Lite）2 款` 被当成品牌。
- 叙述式只认**拉丁字母开头**的品牌名，所以中文叙述里的「前 10 名」「7 个自营」不会被当成品牌；
  `；`「，」「、」「。」「:」都能当分隔符，`Sandberg（Streamer Pro Elite）1 款` 这种括号型号也能正确取出 Sandberg。
- 两种写法进的是同一套关联：竞品页「品牌 × 客户关联」、客户详情「关联竞品」、入驻预判的 SKU 统计都同步。
  只有「没量化」的品牌在表格里显示「—」，不参与 SKU 求和。

### 竞品页的「三档」，别把有品牌的算成缺失（2026-11-20）

`竞品与入驻预判` 页原来只按「有没有解析出款数」分两档，于是 BCC 这种体量列写了 `Logitech、Insta360`
但没写款数的客户被丢进「竞品数据缺失」——品牌明明认出来了，却显示成没数据。现在按线索完整度分三档：

| 档位 | 判定 | 页面位置 |
|---|---|---|
| 有款数 | `sku.brandCount > 0` | SKU 结构矩阵 / 入驻预判清单 |
| **有品牌、缺款数** | 款数为 0，但 `COMP.of()` 有品牌（体量列只写品牌名、或简介/备注提到） | 单列一张表，列出已认出的品牌 + 「补什么」 |
| 竞品数据缺失 | 款数为 0 且一个品牌都认不出（空着 / 「/」「—」/ 备注也没提） | 原来的缺失清单 |

同时「名单阶段」的文案也不再一律说「体量 / 竞品 / 产品线均未调研」：已填竞品品牌的会写成
「已认出竞品品牌、但没写款数，补齐款数与价格带再做型号预判」，并在依据里带出体量列原文。
- 品牌底表（`comp.js` 顶部 `SEED`）本轮补了 **Rapoo（雷柏）/ Sandberg / HAMA**；ISY 是 MediaMarkt 自有品牌，
  不进底表但在关联里照常出现（竞品档案会显示「档案未收录」，这是事实）。

**看板上多出来的两处**
1. 竞品页（零售「竞品与入驻预判」/ 代理「产品线与竞品」）新增**品牌 × 客户关联**卡片：
   每个品牌给出关联客户数（零售 / 代理分列）、合计 SKU、来源分布（体量列 67 · 简介 3）、档案行数与竞争关系；
   点开是客户清单（点名字直接打开该客户详情）与命中原句。
2. 客户详情新增**关联竞品**表：品牌 / SKU / 价格带 / 档案里的竞争关系与 OBSBOT 对位型号 / 同品牌另 N 家。

**归一与排除规则**（`src/comp.js`）
- 同一家公司的不同写法归一：`PTZ Optics` = `PTZOptics`、`BZB GEAR` = `BZBGEAR`、`Hewlett Packard` = `HP`、
  `罗技` = `Logitech`、`ThinkVision` 归到 `Lenovo`、`Adessp` 这类拼写错误归到 `Adesso`。
- **`AVer`（圆展）与 `AVerMedia`（圆刚）是两家公司，不合并** —— 体量列/档案里两种写法都真实存在。
- 噪声不算品牌：`官网未揭露`、`/`、`Webcam`、`PTZ Camera`、`无` 等。
- **否定句不算**：「不代理 Logitech」「未做 Yealink」不会产生关联。
- `OBSBOT / 寻影` 是我方，不进竞品关联（在架情况另有统计）。
- 品牌底表在 `comp.js` 顶部 `SEED`，加一行就多一个可识别品牌（含中文别名）。

**同步方式**：关联是**实时派生**的，不是另存一份对照表。
改原表字段（含人工覆盖）、写跟进备注、云端同步回来，下一次渲染就按指纹自动重算（实测 806 家客户重建约 27ms）；
`update.py` 重跑 Excel 后重新构建，新客户/新竞品自然进来。**没有新增云端列，同事不用再跑建表 SQL。**

**已知边界（如实说明）**：自由文本匹配只认品牌底表里的词。全新品牌第一次出现时，
如果它既没进 `客户字段`、也没进竞品档案，就不会被识别 —— 往 `SEED` 加一行即可（这是刻意的：
宁可漏认，也不把普通英文单词当成品牌）。

| 档 | 词表（节选） | 结论 |
|---|---|---|
| ① 零售身份词 | 零售商 · 零售店 · 零售连锁 · 零售集团 · 零售巨头 · 零售平台 · 零售品牌 · 零售门店 · 线上零售 · 网络零售 · 零售电商 · retailer · retail chain · retail giant | **零售**（若「系统集成商 / 方案商 / 设计公司」出现得更早，改判代理） |
| ② 门店 / 电商形态 | 门店 · 实体店 · 旗舰店 · 专卖店 · 集合店 · 乐器店 · 相机店 · 会员店 · 卖场 · 超市 · 商超 · 百货 · 商城 · 网店 · 电商 · 线上销售 · 直播带货 · 2C · toC · B2C · DTC · e-commerce · online store · marketplace | **零售**，但要求出现在第一个集成 / 渠道词之前 |
| ③ 集成 / 分销 / 服务身份 | 系统集成商 · 方案商 · 分销商 · 经销商 · 代理商 · 供货商 · 销售商 · 安装商 · 租赁商 · 服务商 · 维修 · IT 服务 · 网站设计 · 集成 · 分销 · 代理 · 租赁 | **代理** |
| ④ 终端自述 | 大学 · 学校 · 医院 · 政府 · 教会 · 电视台 · 媒体 · 制作公司 · 厂商 · 平台 · 协会 | **代理 · 终端·非渠道** |
| 都没有 | — | **代理 · 待核实**（孤立的「零售」「销售」二字不算身份） |

三条容易踩的细则：

1. **孤立的「零售」不算身份**：「设备零售」「零售租赁」「零售/经销商」里的零售只是顺带说一句；
   要判零售，得有身份名词（零售商 / 零售店…）或门店电商形态。
2. **谁先出现谁是主身份**（仅在第 ② 档）：「拥有 3 家门店的系统集成商」仍归代理，
   「9 家门店的相机零售商」归零售。
3. **「服务零售商」不是身份**：「为零售商供货的分销商」「面向零售商与集成商」这类写法，
   零售只是它的客户群，会被跳过。

**前端与后端共用一份词表**：`build_v5.py` 把 `classify_new.py` 里的正则注入页面
（`window.CLASSIFY_RULES`），「客户录入」页的单条录入与批量导入走 `src/classify.js` 的同一套判定，
不会再出现「上传时进零售表、重建后又被判回代理」。词表只有一处要改。

**官网核验（可选增强）**：简介判不出来、或只写了「销售 / 供货」时，可以抓官网首页找交易证据：

```bash
python src/site_probe.py                 # 只抓新增名单里还没抓过的候选（约 1–2 分钟）
python src/site_probe.py --all           # 全部重抓
python src/site_probe.py --names "Logesco,firefold"
```

判定证据只有四种：电商平台指纹（Shopify / WooCommerce / BigCommerce / Magento）、
加购与结账、标价、商品导航。**有「方案 / 设计 / 案例」话术的站点不判零售** ——
这类公司常有线上商城但主业是项目集成（CCI Solutions、The Penn Group 就是这种）。
抓不到（403 / 超时 / DNS）如实记 `unknown`，不猜。结论存 `data/site_verdict.json`，
构建时只读缓存、不联网，方法页「八、客户身份判定」会把**官网与简介不一致**的客户列成清单。

**人工复核优先**：`data/lead_classify.json` 的 `overrides` 优先级最高（格式
`{"客户名": {"type":"retailer|agent","seg":"零售|渠道|终端·非渠道|待核实","why":"理由"}}`）。
构建时会拿「纯规则」把它对一遍，不一致就打印 `口径自检` 告警 —— 复核仍然生效，但漂移看得见。

**本轮改动结果**：新增名单判零售从 81 家降到 57 家，10 家改判代理（STR Micro、Parro Info、
Logesco、MelroseMAC、Projector Reviews、origin pc、AV Gear、The Broadcast Shop、
epic rise electronics、firefold），2 家双身份客户按「零售在前」改判零售（Mastervox、voIP Supply）。
原表 65 家零售商**未动** —— 那是原始 Excel 的定稿口径（很多简介写成「总部位于…的连锁巨头 / 单店」），
要不要按新门槛复核另说，改判需要走 `data/base_reclass.json` 并同步 `data/pipe_alias.json`（跟进记录 id 含类型）。


源表之外，同事可以直接在页面里加新客户：顶部页签「客户录入」→ 填表 → 点「保存并加入看板」，**立刻写进云端**，别人 6 秒内刷到。

- **存哪儿**：云端 `customers_extra` 表（不是源表）。`北美渠道客户整理.xlsx` 每次 `update.py` 重跑都会覆盖内置数据，手工录的存进去会被冲掉；存云端既不被覆盖，也能多人共享。

  没填就留空，跟进表显示「待指派」，不计入任何人的负责人负载。
  历史上「新增名单默认 Evelyn」只适用于 2026-11 那一次（`北美客户新增.xlsx`，`markLead()` 里保留），
  不是往后的默认。云端曾经被自动填成 Evelyn 的 145 行已清空（备份：`data/backup/customers_extra_before_owner_fix_*.json`）。

  在零售商视图里是看不到的（页签上的数字也只统计当前类型，例如「客户录入 92」= 零售侧 92 家，代理侧另有 60 家）。
- **合并方式**：页面启动时把这张表拉下来，由 `model.js` 并进客户列表，批次为「名单阶段」（不跑 P 码三因子、不给主推型号），细分单独一档 **手工录入**（跟进页的细分筛选里能一键只看）。
- **去重**：同名（忽略空格与大小写）不能重复录；若看板里已有同名客户，会提示直接去「开发跟进」补进度。
- **删除**：下面那张「手工录入的客户」表格里有「删除」，只删这条手工录入，源表客户不受影响。
- **实时性**：保存成功即写库；其他人靠 6 秒轮询自动更新。轮询到变化时会重建客户列表，但**不会清掉你正在填的表单**（提交前会先把输入框的值存一遍再还回来）。

## 跟进进度导入（Evelyn 的进度表）

Evelyn 用一份 Excel 记新增名单的触达情况（`Evelyn北美客户开发进度情况-*.xlsx`，列：国家 / 客户名 / 优先级 / 一句话简介 / 官网 / 覆盖区域 / 主要品类 / 当前阶段 / 已完成动作 / 下一步动作 / 负责人 / 计划跟进 / 最近跟进）。导入分两步：

```bash
python src/extract_evelyn.py "<进度表.xlsx>"   # 1) 映射成看板的记录 id → data/evelyn_sync.json
python src/push_pipe.py                        # 2) 写进云端 pipe_records（页面刷新即见）
```

- **名字怎么认**：按「去引号 / 去标点 / & → and / 去公司尾缀」归一后比对，与 `build_v5.py` 的去重同口径；归一对不上的写进 `data/pipe_alias.json`（例如 `full compass` → `Full Compass Systems`、`Camera Corner` → `Camera Corner Connecting Point`、`Applied Electronics Edmonton` → `Applied Electronics`）。
- **类型以看板为准**：进度表虽然叫「代理集成商」，里面也混着零售侧客户，所以 `ctype` 取看板自己的分类结果，不按 sheet 名走。
- **同一个客户写了两行**（`Marco Bernard` / `Marco Bernard consultant`）：留「最近跟进」更晚的那条。
- **不覆盖原表客户**：进度表里还有 16 家原本就在原表里的客户（Walmart、Vistek、Samy's Camera…），她表里多数停在「已建联」，而看板上这些已到「已合作·维护中」，直接覆盖等于把进度改回去，所以默认跳过，要覆盖加 `--all`。
- **写入通道**：`/.cloud/database/rest/pipe_records` + 发布密钥 + 精确来源匹配的 Origin 头，与页面手填完全同构，所以不需要重新发布页面。

## 抽屉里直接补跟进记录（含备注，可换行）

「开发跟进」页点客户名，右侧抽屉**最上面新增一块「跟进记录」**，四个字段都能直接写，都是多行文本框：

| --- | --- | --- |
| 已完成动作 | `pipe_records.done_action` | 与表格里的「已完成动作」列同一份数据，改哪边另一边都变 |

## 性能：为什么以前越更新越卡（2026-11-25 已修）

看板是**单文件离线 HTML**，所有数据、脚本、GeoJSON 都内联在同一个文件里，每次打开都要整份下载 + 解析。客户数从 700 涨到 806 之后，有两处写法把成本放大了，已经改掉：

| 问题 | 原因 | 改法 | 效果（真实 Chrome 实测） |
|---|---|---|---|
| 首屏要等 0.7 秒才出表格 | 530KB 数据写成了 **JS 对象字面量** `window.__DATA__ = {...}`，V8 解析对象字面量是慢路径 | 构建时改成 `JSON.parse("…")`（`build_v5.py: js_json()`），V8 走快路径 | 首屏 **688ms → 205ms** |
| 竞品页 / 抽屉每次打开都顿一下 | `comp.js` 的 `of(c)` 每次调用都重算一遍**全库指纹**（806 家 × 全部文本字段滚哈希）。第 42 轮把「体量列兜底识别」改成无条件执行后，这项开销被放大 | 指纹改成 `APP.ver` 版本号：`model.build()` 与 `pipe.js` 每次落库各 +1，缓存只在版本变化时失效 | 806 次 `of()` **905ms → 12ms**；竞品页 354ms → 11ms |
| 打开页面后要等云端数据才「活」 | 跟进表 / 手工录入 / 覆盖表**串行**拉，三次往返叠着走 | 一次 `Promise.all` 并发，且首屏不再 `await`（先渲染再回填） | 首屏不再等网络 |
| 每 6 秒轮询会重算一次品牌索引 | `applyRemote()` 无条件 `save()` → 版本号被推高 | 只有内容真变了才落库 | 空闲轮询回到 0 开销 |

另外加了一个首屏占位（`#bootload`，`UI.init()` 跑完就删），下载那 1–3 秒里显示「正在装载渠道客户数据…」，不再是白屏。

**还能再快的地方（没做，评估过）**：托管站对 HTML **不做 gzip**，1.18MB 原样传输（TTFB 0.5–2.4 秒，下载再 +0.45 秒）。这层只能靠托管侧压缩，改前端代码动不了；如果哪天换成会压的托管（GitHub Pages 就会），首屏还能再快 0.3–0.4 秒。

改完之后，如果哪天又觉得卡，先按这个顺序量：

```bash
node --max-old-space-size=8192 smoke5.js          # 功能有没有坏
node perftest.js "全球渠道总看板.html"             # 首屏 & 各视图耗时（先起一个 9333 端口的无头 Chrome）
```

- **按字段保存**：两个人同时改同一家的不同列不会互相覆盖；改同一列以最后一次提交为准。
- 写入失败会做 3 次短退避重试，仍失败则入队，每 2.5 秒再试；改动没写进云端就关页面，浏览器会弹出确认提示。

## 云端同步的双通道（WorkBuddy / Supabase，2026-11 新增）

WorkBuddy 云服务的数据库资源是按额度计费的，欠费/超限时接口返回 `DATABASE_RESOURCE_ISOLATED`（HTTP 402），所有读写被暂停。为了让协作功能不再依赖这一块额度，看板支持**第二条同步通道：Supabase**（免费档，独立账号），两边表结构逐列一致，随时互切、数据互搬。

### 切到 Supabase 的步骤

1. 注册 [supabase.com](https://supabase.com)（免费），建一个 Project，区域随意（选近的如新加坡/东京延迟低）。
2. 在 SQL Editor 里粘贴执行 **`deploy/supabase_schema.sql`**（建两张表 + 时间戳触发器 + RLS，一次完成）。
3. 在 **Project Settings → API** 里复制 **Project URL** 和 **anon public key**（不是 service_role key），填进 **`data/supabase.json`**，并把 `"enabled"` 改成 `true`。
4. `python src/migrate_to_supabase.py --check` 验证连通 → `python src/migrate_to_supabase.py --seed` 灌入本地种子（Evelyn 新增名单 680 条 + Awevoke/Shure 两家）。
5. `python build_v5.py && python publish.py` 重新发布。跟进页角标出现「**同步·Supabase**」即切换成功。

### 切回 WorkBuddy

把 `data/supabase.json` 的 `"enabled"` 改回 `false`，重新构建发布即可，一行代码都不用动。角标不再显示「同步·Supabase」就是回到了 WorkBuddy 通道。

### 数据搬运

`src/migrate_to_supabase.py` 三个模式：

| 命令 | 作用 |
|---|---|
| `--check` | 验证 Supabase 连通与建表是否完成 |
| `--seed` | 把本地种子灌进 Supabase（Evelyn 新增名单的 680 条跟进记录 + 2 家手工录入客户） |
| `--from-workbuddy` | 从 WorkBuddy 云库全量拉取再写入 Supabase（**需 WorkBuddy 额度已恢复**；会把 Cyan 填的原表客户记录等所有行搬全） |

迁移是**按 id 合并**（upsert），不会清空 Supabase 里已有的更新；推荐先 `--seed` 保底，等 WorkBuddy 额度恢复后再跑一次 `--from-workbuddy` 把旧库补全。

### 安全定位

Supabase 的 anon key 与 WorkBuddy 的 publishableKey 同级：**公开可读写**，只承载跟进记录、客户名这类非敏感协作数据，别放机密信息。RLS 策略与 WorkBuddy 侧一致（anon 全开），属于「知道链接就能填」的定位，和现在的共享版相同。



### 跟进页的两个视图操作

- **点负责人负载的条形 = 只看这个人的客户**：右上「负责人负载」里每根条都可点，点一下就筛出该负责人名下的客户（表格上方出现「只看 Evelyn · 614 家 ×」的小胶囊，点 × 或再点同一条即可恢复）。筛选只作用于跟进表，不影响其它页签；切换「全部 / 新增 / 原表」或细分时若这个人已不在当前范围，筛选会自动清除，不会出现空表。点条形时其它负责人会变淡，方便看清当前在看谁。
- **收起图表 = 把纵向空间让给列表**：跟进表上方那张「开发阶段分布 + 负责人负载」可以收起来（点卡片右上角「收起图表」），收起后列表可滑动区域从约 10 行扩到约 14 行；状态记在本机浏览器，下次进来保持上次的选择。展开时表格高度是 `max(380px, calc(100vh - 215px))`，收起时是 `max(340px, calc(100vh - 400px))`。
